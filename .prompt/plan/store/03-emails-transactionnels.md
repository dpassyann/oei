# Boutique OEI — emails transactionnels

## 0. Démarcation Keycloak vs Spring Mail (confirmation explicite demandée par le porteur de projet)

**Les emails d'activation de compte, de confirmation d'inscription, et de MFA (code/lien de vérification à deux facteurs) sont gérés par Keycloak lui-même** (SMTP configuré côté realm Keycloak + thème email Keycloak déjà custom sur ce projet — voir la règle mémoire "Thèmes Keycloak custom" : login+account+admin+email doivent tous matcher la charte OEI). **Ils ne doivent pas être réimplémentés côté backend Spring.** Ce chantier n'introduit aucune duplication de cette responsabilité : le backend Spring ne touche jamais aux emails de cycle de vie de compte (création, activation, réinitialisation de mot de passe, MFA) — c'est strictement le rôle de Keycloak et de son thème email déjà en place.

Ce que le backend Spring **doit** envoyer, lui, ce sont des emails de **réassurance métier** liés à des actions qui n'ont de sens que côté application (Keycloak ne les connaît pas) : confirmation de paiement, confirmation de commande, accusé de réception d'une contribution, etc.

## 1. Fournisseur SMTP et mécanisme d'envoi

- **Fournisseur SMTP : Amazon SES**, cohérent avec l'infrastructure AWS déjà décidée pour ce projet (voir `.prompt/plan/final/00-AWS-DEPLOYMENT-AND-DEVOPS-PROMPT.md`). Configuré via Spring Mail standard (`spring.mail.host`/`port`/`username`/`password` pointant vers le endpoint SMTP SES de la région choisie), pas le SDK AWS SES direct (`software.amazon.awssdk:ses`) — Spring Mail + SMTP est suffisant ici et reste cohérent avec le choix Thymeleaf ci-dessous ; garder l'option SDK direct ouverte seulement si le porteur demande plus tard des fonctionnalités SES avancées (templates SES natifs, tracking d'ouverture SES) que Spring Mail ne couvre pas.
- **Templating : Thymeleaf**, avec un template HTML + un fallback texte brut par email (multipart MIME `text/plain` + `text/html`, jamais HTML seul — accessibilité et clients mail qui ne rendent pas le HTML). Utiliser `spring-boot-starter-thymeleaf` + `spring-boot-starter-mail`, `JavaMailSender` + `MimeMessageHelper` pour construire les messages multipart, `TemplateEngine` (mode `HTML` pour la version riche, un template texte séparé — ou une extraction texte simplifiée du même contenu si le porteur préfère limiter la duplication de templates ; par défaut V1 : deux templates distincts par email pour un rendu texte réellement soigné, pas juste un fallback dégradé).
- Convention de nommage des templates (à respecter, cohérent avec le reste du projet — commentaires de code en anglais, mais contenu utilisateur en français puisque le site est francophone) : `src/main/resources/templates/email/<nom-email>.html` et `.../email/<nom-email>.txt` (ou `.txt.ftl`/`.txt`-équivalent Thymeleaf `TEXT` mode).

## 2. Liste des emails à envoyer (identifiés dans le code déjà écrit)

Emails explicitement demandés par le porteur de projet :

1. **Confirmation de paiement d'abonnement** (cotisation membre — `MemberMembershipFeeApi`/`payMyMembershipFee`, déjà implémenté dans `domain/shared/src/main/java/global/oei/domain/shared/membershipfee/`) — déclenché quand `PayMembershipFeeUseCase`/`PayMembershipFeeService` complète un paiement de cotisation avec succès.
2. **Email de contribution** — accusé de réception d'une contribution de contenu normatif (`MemberContributionsApi`/`createContribution`, `domain/shared/src/main/java/global/oei/domain/shared/content/ContentContribution.java`) — déclenché quand `CreateContentContributionService` enregistre une nouvelle contribution au statut `PROPOSED`.
3. **Confirmation de commande boutique** — déclenché quand une `Order` de ce nouveau chantier passe à `PAID` (voir `02-paiement.md §1`).

Autres cas de réassurance identifiés dans le code déjà écrit (à évaluer/prioriser avec le porteur — proposés ici parce qu'ils suivent exactement le même schéma "interaction significative méritant un accusé de réception", mais **pas explicitement confirmés** par le porteur de projet ; à activer seulement si validé, ou à implémenter en même temps si le porteur ne s'y oppose pas puisqu'ils sont peu coûteux une fois l'infrastructure d'emails en place) :

4. **Certification déclarée puis validée** — quand une `Certification` passe de `DECLARED` à `VALIDATED` (validation admin, `AdminMembersApi`/`validateCertification` déjà implémenté) — le membre est notifié que sa certification est officiellement reconnue par l'OEI.
5. **Badge attribué** — quand un `BadgeAward` est créé pour un membre (`awardBadge`, déjà implémenté) — notification de gamification, cohérente avec l'objectif produit "valoriser la progression et l'engagement du membre" (`.prompt/plan/02-espace-membre.md §1.3`).
6. **Charte éthique signée** — accusé de signature (`signEthicalCharter`, déjà implémenté) — confirmation simple, faible priorité, à considérer optionnelle.
7. **Demande de vérification traitée** (approuvée/rejetée) — `MemberVerificationApi`, `approveVerificationRequest`/`rejectVerificationRequest` déjà implémentés — le membre est notifié du résultat.
8. **Rattachement institutionnel approuvé** — `approveInstitutionAffiliation` déjà implémenté — le membre est notifié qu'il est rattaché à son institution (utile pour le statut Gold automatique, cf. `.prompt/plan/02-espace-membre.md §1.5`).

**Recommandation d'implémentation :** construire l'infrastructure email (§3) de façon générique dès le départ (un seul `EmailPort`/adapter Thymeleaf+Spring Mail réutilisable), puis démarrer par les 3 emails explicitement demandés (items 1-3). Les items 4-8 peuvent être ajoutés en quelques lignes chacun une fois l'infrastructure en place (un nouveau template + un appel au port depuis le service concerné) — à faire dans la même passe d'implémentation si le temps le permet, sinon documenter comme TODO explicite plutôt que laisser une infrastructure à moitié utilisée.

## 3. Modèle technique

- Port de sortie `EmailPort` (ou plus fin-grained : un port par famille d'email si les données envoyées diffèrent trop pour un seul type de commande générique — à trancher en implémentation ; par défaut : un seul `EmailNotificationPort` dans `domain-shared` avec une méthode par cas d'usage explicite, ex. `sendMembershipFeePaymentConfirmation(MembershipFeePayment payment, Member member)`, `sendOrderConfirmation(Order order, Member member)`, `sendContributionAcknowledgement(ContentContribution contribution, Member member)` — pas une méthode générique `send(EmailType type, Map<String,Object> data)` qui perdrait le typage et la lisibilité métier).
- Implémentation dans un nouveau module ou package infrastructure (`infrastructure/persistence` n'est pas le bon endroit — proposer soit un nouveau module `infrastructure/mail` si le projet veut garder `infrastructure/` en parent multi-module explicite, soit un package `infrastructure/notification` si un module dédié semble disproportionné pour un seul adapter — décision à prendre en cohérence avec la structure du parent `infrastructure/` déjà en place ; **recommandation** : nouveau module `infrastructure/mail`, cohérent avec le fait que `infrastructure/client` est lui aussi créé dans ce même chantier, voir `04-architecture-technique.md §1` — le parent `infrastructure/` devient ainsi `persistence` + `security` + `wiring` + `client` + `mail`).
- Chaque email réel envoyé (pas seulement composé) doit être asynchrone du point de vue de la requête HTTP qui déclenche l'action métier (le paiement/la contribution ne doit jamais échouer parce que l'envoi SMTP est lent/en échec) — utiliser `@Async` (Spring) avec un pool dédié, ou un simple `@EventListener` asynchrone sur un événement de domaine déclenché par le service (`OrderPaidEvent`, `ContributionSubmittedEvent`, etc.) plutôt qu'un appel bloquant direct dans le service métier. Un échec d'envoi email est loggé (niveau `WARN`/`ERROR`) mais ne doit jamais faire échouer/rollback la transaction métier associée.

## 4. Tests

- Test unitaire du port/adapter email : ne pas envoyer de vrais emails dans les tests (ni en CI, ni en local) — utiliser soit un `JavaMailSender` mocké (Mockito) pour vérifier que le bon template est résolu avec les bonnes variables, soit **GreenMail** (serveur SMTP de test en mémoire, pattern courant Spring Boot) pour un test d'intégration plus réaliste vérifiant le contenu MIME multipart réellement généré — à choisir en implémentation selon le niveau de confiance voulu ; recommandation : un test unitaire (mock) pour chaque cas d'usage + un test d'intégration GreenMail pour au moins un cas représentatif (confirmation de commande) pour valider que le HTML+texte multipart est bien formé de bout en bout.
